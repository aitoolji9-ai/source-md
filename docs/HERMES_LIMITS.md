# Hermes 한도와 장시간 PDF 작업 — 0.9.5

OCR 요청 수, 터미널 대기 시간, Hermes 모델 호출/문맥 예산은 서로 다른 한도다. 0.9.4는 첫 번째 문제를 쪽별 초기 OCR과 체크포인트로 고쳤다. 0.9.5는 여러 권을 한 번의 유한한 프로그램 작업으로 처리하고 같은 결과 루트에서 상태 확인·재개하게 한다. 모델 한도를 늘리거나 사용 내역을 초기화하지 않는다.

## 프로그램과 스킬

```sh
uv run --frozen preserve-md batch '/원본/PDF폴더' --out '/결과/새작업'
uv run --frozen preserve-md status '/결과/새작업'
uv run --frozen preserve-md resume '/결과/새작업'
```

스킬에서는 같은 인수를 `python3 <skill_dir>/scripts/run.py`에 전달한다. `batch-job.json`이 원본의 절대 경로·해시·쪽수·권별 출력 위치를 고정한다. 바로 아래 PDF만 조사하며 하위 결과/재시도 PDF를 섞지 않는다. 권별 출력은 `01/00_원본복원.md`, `02/00_원본복원.md` 순서다. 원본 사본·자산·좌표를 함께 보관한다.

`--max-pages 20`을 `batch` 또는 `resume`에 추가하면 이번 실행 전체의 페이지 작업 20개 후 종료3으로 저장한다. 여러 권에 각각20개를 허용하는 옵션이 아니다. 기본값은 유한하게 확정된 원본 목록 전체를 처리하는 것이다. 한 권의 실패가 다른 권의 첫 처리를 막지 않으며 같은 명령 안에서 실패를 무제한 재시도하지 않는다. 원본 변경은 어떤 책도 추가 처리하기 전에 검출해 중단한다.

완료 후 재개도 원본·페이지·문서 묶음 무결성을 검사하며 완료 페이지의 OCR과 MD 바이트를 바꾸지 않는다. `status`는 읽기 전용 상태 조회로 무결성 검사를 대신하지 않는다. `writer_active=false`라면 그 결과의 현재 쓰기 실행은 없는 것이다.

## Hermes 기본 실행 도구로 계속하기

설치된 Hermes의 실제 도구 스키마에 다음 옵션이 있는지 확인한다. 현대 Hermes의 예시이며 엔진 설치기가 Hermes를 설치하거나 업데이트하지는 않는다.

```json
{
  "command": "python3 '<skill_dir>/scripts/run.py' batch '/원본/PDF폴더' --out '/결과/새작업'",
  "background": true,
  "notify": true,
  "heartbeat": 0,
  "persist_on_release": true
}
```

- `background`는 짧은 전경 대기와 분리해 프로세스를 추적한다. 반환된 프로세스를 다시 시작하지 않는다.
- `notify`는 지원되는 대화에서 종료 시 알림을 요청한다. Kanban·일회성 작업·알림 비활성 설정은 나중 알림이 지원되지 않을 수 있다. 실제 도구 반환을 보고 유한 대기나 상태 반환을 선택한다.
- `persist_on_release`는 사용자가 대화 종료 뒤에도 계속하기를 요청한 유한한 작업에 사용한다. 세션 정리·압축·실행 예산 종료에 따른 작업 정리에서 해당 프로세스를 유지한다. 명시적 중지나 호스트 종료는 별개다. 새 세션에 기존 대화의 완료 알림까지 전달된다는 뜻은 아니다.
- `heartbeat`로 주기적인 알림을 만들면 추가 모델 턴이 필요할 수 있다. 기본0과 종료 알림을 사용하고 진행 상황은 작은 `status`로 필요할 때 조회한다.

실제 사용 명칭·수명 규약은 [Hermes 공식 도구 안내](https://hermes-agent.nousresearch.com/docs/user-guide/features/tools)와 [실행 도구 소스](https://github.com/NousResearch/hermes-agent/blob/main/tools/terminal_tool.py)를 확인한다. 구버전은 `notify_on_complete`라는 별칭을 쓴다. 핵심 코드를 고치거나 전역 `max_turns`, 실행 예산, 승인 정책을 완화하는 방식으로 해결하지 않는다.

## Hermes Python 환경 분리

실제 Hermes 실행에서 호스트 Python의 `PYTHONPATH`가 엔진의 다른 버전 Python에 전달되어 Pillow의 `_imaging` 확장을 불러오지 못하는 문제가 재현됐다. 스킬 실행기는 연결된 엔진 Python을 `-I -m source_preserve_md`로 호출한다. 호스트의 Python 경로·현재 폴더 동명 모듈을 제외하면서 문서 상대 경로의 작업 폴더는 유지한다. 엔진 패키지가 연결된 환경에 설치되어 있어야 하며 `install-skill`의 기존 연결 규약은 유지한다.

## 한도 오류 판정과 재개

1. OCR은 결과의 `ocr`, `processing`, 실패한 쪽과 요청 수로 확인한다. 기본 PDF 본문 모드는 대상 쪽당 초기 인식1회이며 심화 한도는 쪽별이다.
2. 전경 시간 초과/백그라운드 전환은 터미널 반환과 프로세스 상태로 확인한다. 한 명령이 끝나지 않았는데 같은 변환을 재전송하지 않는다.
3. 모델 호출·문맥·제공자 제한은 Hermes의 실제 오류와 해당 실행 설정/소비를 확인한다. 과거 실험의12회·180초를 현재 모든 업무의 한도로 사용하지 않는다.
4. 작업이 살아 있으면 상태만 조회한다. 종료됐으면 같은 루트에 `resume`한다. `/reset`, 새 티켓, 원본 분할본 생성으로 이미 쓴 예산을 지우거나 처리 완료 쪽을 다시 읽지 않는다.

자동 처리 완료와 문자별 OCR 정확도 인증은 구분한다. 이 변경은 새 OCR 모델을 추가하거나 기존 손글씨 오류율 개선을 주장하지 않는다.
